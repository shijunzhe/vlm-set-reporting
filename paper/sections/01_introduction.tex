Vision-language models are now asked to report a set of objects in an image: to count them, to box them, to parse every element of a screen, or to pick the one element a user means. A typical answer has two parts. The first is a \emph{list}: one entry per object, each giving a class name and a location (a point or a box). We call each entry a \emph{record}. The second, when it is requested, is a \emph{stated count}: the numbers the model writes for how many objects of each class it found. Code can also count the records in the list; we call that the \emph{list count}. The two counts should agree. Often they do not.

Figure~\ref{fig:teaser}a shows one response of GPT-6.1 to a dense synthetic scene with 173 shapes of five classes. Its list has 173 records, and each record matches a different shape of the same class within 20 pixels, so the list is exact. In the same response, the model states counts that add up to 188. Across 50 such scenes, GPT-6.1 wrote an exact list in 20 scenes, and in 19 of them its stated counts were wrong. Sonnet 5.5 wrote an exact list in 39 scenes (after mapping its word ``diamond'' to the class ``square''), and its stated counts were wrong in all 39. The response contains a correct enumeration; the model's own summary of that enumeration is not faithful to it.

Visual set reports are becoming the interface between perception models and the systems that use them: inventory counts, document layout, screen parsing for computer-use agents, click targets. Practitioners compensate with folklore: ask again, ask the model to check itself, overlay a grid, tell it not to miss anything, vote across models. Some of these help, some do nothing, and some make things worse. Without a model of where reporting errors come from, there is no way to predict which. Our thesis is that \emph{reporting is part of the visual task, not merely its formatting}: what a model delivers depends on how it is asked to report, how the report is decoded and read, and how several reports are combined, and each of these steps can be analysed and improved.

\paragraph{What we do.} We describe reporting as a chain with four objects (Figure~\ref{fig:chain}): a \emph{response}, the raw text of one call to a model; the \emph{records} decoded from it; a \emph{set} of records built from one or more responses, for example by keeping only records that two calls agree on; and the \emph{task answer} read from that set, such as a count per class or a click point. Three quantities connect the chain to every loss we study: the maximum number of records that can be paired one-to-one with true objects under the task's matching rule, the number of records that are scored, and the rule that reads the answer. They give exact relations for what each operation does. Deleting unconfirmed records lowers the error exactly when, on average, fewer than one in two of the deleted records were matched (the threshold depends on the costs of the two error types), whichever model or view supplied the confirmation. Averaging the coordinates of agreeing records is a separate effect that can help or hurt. The chain takes reports as they come: from one call on the whole image, or from several views produced by an existing view planner such as tiling or zoom, whose merging and cross-view confirmation are constructions like any other. Alongside these relations we state a behavioural model, kept separate from them: each object has a persistent tendency to be reported or missed, partly shared across models. This analysis of what a model reports complements analyses of what a single call can see \citep{shi2026zoomin}.

\paragraph{Three problems, kept apart.} Practice often treats three problems as one. \emph{Detecting} that a report is wrong can be done without labels, from disagreement between reports (Proposition~\ref{prop:alarm}). \emph{Judging} which of several reports or configurations is more accurate cannot be certified from outputs alone (Proposition~\ref{prop:nocert}); it needs labels, or a configuration chosen on other data and carried over (Proposition~\ref{prop:approx}). \emph{Repairing} a report works when the needed information is already available: in another field of the same response, in another view of the image, or in another model's report. A method that detects errors well need not judge well, and one that judges well need not repair. The paper is organized around this distinction.

\paragraph{What we find.} Measured against common remedies on the same stored calls (Table~\ref{tab:common}), the defaults derived from the theory do best where it predicts they should.
\begin{itemize}
\item \textbf{Repair the readout.} On dense synthetic scenes with five classes, counting the list instead of reading the stated count cuts per-type count error by 71\% to 84\% in the same responses of GPT-6.1 and Sonnet 5.5; on one-class photographs the difference is not significant. The full list-first protocol (list before counts, row-by-row scan, declared class aliases, and the readout of Section~\ref{sec:method}) cuts it by 85.2\% and 98.8\% at the cost of one call; self-consistency, the median of the stated counts of three repeated calls, gains at most 23\%. For Gemini 3.8 at its lowest reasoning setting, whose lists often break, the change is $+15.6\%$ and not significant (interval $-5.3\%$ to $+39.4\%$); at the same output cap its default setting lowers the error by 53.6\%. On aerial and document images with several classes the lists themselves miss objects, the stated count stays close to the list, and the protocol changes count error by $-20\%$ to $+0.4\%$ for GPT-6.1 and Sonnet 5.5, none significantly, and by $-25.8\%$ (DocLayNet) and $-28.2\%$ (DOTA, interval reaching zero) for Gemini 3.8 at its default setting. When the label-free gap between the two counts is small, switching between them can change the error by at most that gap (Sections~\ref{sec:res:readout} and \ref{sec:res:degen}).
\item \textbf{Repair the set.} Set error counts false records plus missed objects. When a second call (the \emph{partner}) is used to confirm the records of a first call (the \emph{base}), the change in set error splits exactly into two terms: deleting the base records the partner does not report, and averaging the coordinates of those it does. Whether deletion helps is decided by one number, the marginal matching rate $p_1$ of the deleted records, and that number can be estimated from very few labels: on 54 base/partner pairs, five labelled images predict whether deletion helps on the other images in 83\% of draws, the task family's default does so without labels in 85\%, and the shipped label rule, which starts from that default and switches only on clear evidence, in 87\%, cutting the loss from a wrong decision from 0.43 to 0.17 errors per image. The averaging term is positive in 37 pairs and negative in 13 (Section~\ref{sec:res:set}).
\item \textbf{Repair the view.} Two-stage zoom cuts click error by up to 65\% (Gemini 3.8; 45\% for Sonnet 5.5, not significant for GPT-6.1); a three-click vote and zooming only on disagreement gain at most 13\%. Tiling helps when every object lies wholly inside some tile. Reports from four crops, used to confirm the whole-image report, cut set error by up to 45\%; where they fail, the deletion threshold explains why (Section~\ref{sec:res:view}).
\item \textbf{Detect.} At a 1.5\% distance threshold, a second, cheaper model catches 61\% of GPT-6.1's click errors (14 of 23) and a second call of the same model 17\% (4 of 23), but the second model flags more items: it leaves 86\% of items to act on without review (the \emph{coverage}) against 96\%. At the same coverage of 93\%, it catches 39\% against 26\%, and only the second model reaches miss rates near 4\% on the items acted on (Section~\ref{sec:res:persist}).
\item \textbf{Judge.} Choosing the best set among three calls of one model, with knowledge of the truth, would remove 45\% of set error; selectors fitted with labels reach 16\%. Constructions, rules that build one set from several calls such as keeping only records that all three calls report, were chosen on five datasets and applied to the sixth; they improve set error on most datasets where models over-report, that is, report more false objects than they miss (Sections~\ref{sec:res:select} and \ref{sec:res:transfer}).
\end{itemize}

\paragraph{Contributions.}
\begin{enumerate}
\item \textbf{A formal account of visual set reporting.} A chain from response to records, set and answer, in which task-compatible matching, scored record counts and the readout express the losses for counts, boxes, screen elements and clicks; exact relations for deletion, coordinate averaging and readout; a constrained oracle for any declared family of candidate sets; and an impossibility result for certifying a report from outputs alone (Sections~\ref{sec:setup} and \ref{sec:theory}).
\item \textbf{Conditions for repetition, new views and second models,} stated as inequalities on how often a partner confirms the base report's correct and incorrect records, together with a behavioural model of persistent errors and the revisions that led to it (Sections~\ref{sec:theory:behaviour} and \ref{sec:method:revise}).
\item \textbf{Procedures and measurements.} Reporting procedures whose every input is named (task specification, shipped configuration, computed from the outputs, or optional labels), released as one entry point that is replayed on the stored calls and evaluated on 46,785 calls to five proprietary models and one open-weight model, with all responses, the labels whose licences allow redistribution, a script that rebuilds the others from the official downloads, and the code that regenerates every table and figure at \url{https://github.com/shijunzhe/vlm-set-reporting} (Sections~\ref{sec:method} and \ref{sec:experiments}).
\end{enumerate}
