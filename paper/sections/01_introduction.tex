Vision-language models are now asked to report a set of objects in an image: to count them, to box them, to parse every element of a screen, or to pick the one element a user means (GUI grounding: given a screenshot and an instruction, return the point to click). A typical answer has two parts. The first is a \emph{list}: one entry per object, each giving a class name and a location (a point or a box). We call each entry a \emph{record}. The second, when it is requested, is a \emph{stated count}: the numbers the model writes for how many objects of each class it found. Code can also count the records in the list; we call that the \emph{list count}. The two counts should agree. Often they do not.

Figure~\ref{fig:teaser}a shows one response of GPT-6.1 to a dense synthetic scene with 173 shapes of five classes. Its list has 173 records, and each record matches a different shape of the same class within 20 pixels, so the list is exact. In the same response, the model states counts that add up to 188. Across 50 such scenes, GPT-6.1 wrote an exact list in 20 scenes, and in 19 of them its stated counts were wrong. Sonnet 5.5 wrote an exact list in 39 scenes (after mapping its word ``diamond'' to the class ``square''), and its stated counts were wrong in all 39. The response contains a correct enumeration; the model's own summary of that enumeration is not faithful to it.

Visual set reports are becoming the interface between perception models and the systems that use them: inventory counts, document layout, screen parsing for computer-use agents, click targets. Practitioners compensate with folklore: ask again, ask the model to check itself, overlay a grid, tell it not to miss anything, vote across models. Some of these help, some do nothing, and some make things worse. Without a model of where reporting errors come from, it is hard to predict which. Our thesis is that \emph{reporting is part of the visual task, not merely its formatting}: what a model delivers depends on how it is asked to report, how the report is decoded and read, and how several reports are combined, and each of these steps can be analysed and improved.

\paragraph{What we do.} We describe reporting as a chain with four objects (Figure~\ref{fig:chain}): a \emph{response}, the raw text of one call to a model; the \emph{records} decoded from it; a \emph{set} of records built from one or more responses, for example by keeping only records that two calls agree on; and the \emph{task answer} read from that set, such as a count per class or a click point. Three quantities connect the chain to every loss we study: the maximum number of records that can be paired one-to-one with true objects under the task's matching rule, the number of records that are scored, and the rule that reads the answer. They give exact relations for what each operation does. Deleting unconfirmed records lowers the error exactly when the deletion loses fewer than one match per two scored records removed (with equal costs of the two error types), whichever model or view supplied the confirmation. Averaging the coordinates of agreeing records is a separate effect that can help or hurt. The chain takes reports as they come: from one call on the whole image, or from several views produced by an existing view planner such as tiling or zoom, whose merging and cross-view confirmation are constructions like any other. Alongside these relations we state a behavioural model, kept separate from them: each object has a persistent tendency to be reported or missed, partly shared across models. This analysis of what a model reports complements analyses of what a single call can see \citep{shi2026zoomin}.

\paragraph{Seeing and reporting.} The title names the two things the chain separates. What a set of calls has seen is its \emph{coverage}: the correct records or candidates present anywhere in the responses, in any field, view or model. What is reported is a \emph{selection} from that coverage: which field is read, which records are kept, which point is output. The repairs in this paper add coverage, improve the selection, or, by averaging coordinates, move the records that are kept; on a fixed set of calls an operation helps exactly when, on what it changes, the errors it repairs outweigh the correct outputs it breaks, at the exchange rate the loss sets (Section~\ref{sec:theory}). Reading the list instead of the stated count, and deleting unconfirmed records, change only the selection. A smaller view or a second model adds coverage, and a selection must then use it: on 600 click items, three models' points with a plain vote have a miss rate not significantly different from that of three calls of one model, and choosing among the same points with a scorer and a comparison removes 18 more misses. Detecting and judging ask what the outputs alone reveal about a selection.

\paragraph{Three problems, kept apart.} Practice often treats three problems as one. \emph{Detecting} that a report is wrong can be done without labels, from disagreement between reports (Proposition~\ref{prop:alarm}). \emph{Judging} which of several reports or configurations is more accurate cannot in general be certified from outputs alone, because two scenes can produce the same outputs (Proposition~\ref{prop:nocert}); it needs labels, on the task itself or on related sources from which a configuration is carried over (Section~\ref{sec:res:transfer}). \emph{Repairing} a report works when the needed information is already available: in another field of the same response, in another view of the image, or in another model's report. A method that detects errors well need not judge well, and one that judges well need not repair. A model asked at run time to score or compare candidate answers, as in our GUI-grounding tier, is one more source of evidence for a repair, not a certificate. The paper is organized around this distinction.

\emph{Will better models make the repairs unnecessary?} Some failures are already absent on our tasks: on our synthetic counting scenes, the average coordinate offset is about 1\% of the matching tolerance, and Gemini 3.8's default reasoning setting removes most of its broken lists. \emph{More calls of the same model, or a different source of evidence?} For counts, clicks and error detection, a different source helped more: another field of the same response, the original pixels of a smaller crop, or a different model. Repeating the same call helps mainly by removing false records that do not repeat.

\paragraph{What we find.} Measured against common remedies on the same stored calls (Section~\ref{sec:res:common}) and, for clicks, on 600 further items (Section~\ref{sec:res:choose}), the shipped defaults do better than these remedies in most comparisons, and the theory's quantities say where and why.
\begin{itemize}
\item \textbf{Repair the readout.} On dense synthetic scenes with five classes, counting the list instead of reading the stated count cuts per-type count error by 71\% to 84\% in the same responses of GPT-6.1 and Sonnet 5.5, and the full list-first protocol cuts it by 85.2\% and 98.8\% at the cost of one call, where self-consistency over three calls gains at most 23\%. On one-class photographs, and on aerial and document images where the lists themselves miss objects, the protocol's change is small and not significant for these two models; Gemini 3.8 needs its default setting, at which far fewer of its lists break (flagged lists 90\% to 12\%) (Sections~\ref{sec:res:readout} and \ref{sec:res:degen}).
\item \textbf{Repair the set.} When a partner call confirms the records of a base call, the change in set error splits exactly into deleting the records the partner does not report and averaging the coordinates of those it does. Deletion helps when the marginal matching rate $p_1$ of the deleted records is below $1/2$; the task family's default decides correctly in 85\% of draws over 54 base/partner pairs, and five labelled images cut the loss from a wrong decision from 0.43 to 0.17 errors per image. Confirmation is a default for set error on over-reporting families only; for F1 the default is a single call (Sections~\ref{sec:res:set} and \ref{sec:res:transfer}).
\item \textbf{Repair the view.} Two-stage zoom cuts the miss rate by 65\% for Gemini 3.8 and 41\% for Sonnet 5.5 (not significant for GPT-6.1), where a three-click vote or zooming only on disagreement gains at most 13\%. Confirming a whole-image report with four crop reports cuts set error by up to 45.5\% and hurts where $p_1>1/2$ (Section~\ref{sec:res:view}).
\item \textbf{Detect.} A second, cheaper model catches 61\% of GPT-6.1's misses and a second call of the same model 17\%, at the price of flagging more items (Section~\ref{sec:res:persist}).
\item \textbf{Repair a click by choosing among models.} The miss rate of one answer chosen among several calls splits exactly into three terms: no correct candidate, no correct cluster representative, a wrong choice among representatives. FSR's GUI-grounding tier, built on this split, misses 9.33\% of 600 ScreenSpot-Pro targets, against 13.67\% for GPT-6.1's two-stage zoom, 12.67\% for three such zooms at about the same cost, and 12.33\% for a plain vote over the same three models' points; against a crop-first baseline the difference, $-2.17$ points, has an interval that reaches zero (Section~\ref{sec:res:choose}).
\item \textbf{Judge.} With the truth, choosing the best set among three calls of one model would remove 45\% of set error; selectors fitted with labels reach 16\%. Defaults chosen on other sources transfer: three-call unanimity improves set error significantly in 9 of 15 over-reporting cells and significantly worsens none, and a single-call configuration chosen on three detection sources raises macro F1 on the fourth from 42.1 to 49.1 (Sections~\ref{sec:res:select} and \ref{sec:res:transfer}).
\end{itemize}

\paragraph{Contributions.} Our contribution is a common task-loss model for visual reporting, procedures that act on its stages, and experiments that separate what information is available from the quality of the answer finally delivered. The model covers multi-record outputs and the single-record case of click grounding. Its exact relations do not prescribe one universal interface; they say what each operation can change and what must be measured to decide whether the change is useful.
\begin{enumerate}
\item \textbf{A common theory of reporting operations and task quality.} A chain from response to records, set and answer, in which task-compatible matching, scored record counts and the readout express the losses for counts, boxes, screen elements and clicks; exact relations for deletion, coordinate averaging and readout; conditions, stated as inequalities on confirmation rates, under which repetition, a new view or a second model helps, with a behavioural model of persistent errors; a constrained oracle for any declared family of candidate sets; an exact split of the error of one answer chosen among several calls, with the effect of adding a source and of switching an answer; and an impossibility result for certifying a report from outputs alone (Sections~\ref{sec:setup} and \ref{sec:theory}).
\item \textbf{Executable procedures for recovering, constructing and selecting visual records.} A default pipeline that dispatches by task and budget, and a several-model GUI-grounding tier, in which every input is named (task specification, shipped configuration, computed from the outputs, or optional labels), together with the revisions of the model that led to them (Section~\ref{sec:method}).
\item \textbf{Mechanism-resolving evidence and a fixed-protocol evaluation of complete task outputs.} Measurements on 67,364 calls to five proprietary models and one open-weight model that attribute gains and failures to single operations, and a 600-item click evaluation of the complete tier. All responses, the labels whose licences allow redistribution, a script that rebuilds the others from the official downloads, and the code that regenerates every table and figure are at \url{https://github.com/shijunzhe/vlm-set-reporting} (Sections~\ref{sec:experiments} and \ref{sec:results}).
\end{enumerate}
