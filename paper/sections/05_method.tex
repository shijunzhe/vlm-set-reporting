\section{Method: A Default Pipeline with Stated Inputs}\label{sec:method}

The pipeline turns an image and a task into a final set, a task answer, a status and an alarm score. Every input it uses comes from one of four named sources: \src{T} the task specification given by the user (classes, alias map, matching rule, loss); \src{S} the shipped configuration, a fixed file released with the code (\texttt{config/default\_pipeline.json}) whose values come from our evaluation on other sources; \src{O} quantities computed from the current outputs; and \src{L} optional labels. No step requires the user to know $p_1$, a partner's quality or the current F1. Algorithm~\ref{alg:pipeline} gives the steps in order. Steps 1 to 6 repair the report, the optional label rule of Step 7 judges between configurations, and the alarm returned in Step 8 detects errors; Section~\ref{sec:method:revise} describes how the model behind these steps was revised.

\begin{algorithm}[t]
\caption{Default reporting pipeline}\label{alg:pipeline}
\small
\begin{algorithmic}[1]
\Require image $x$; task $\delta=(\mathcal{C}_\tau,\alpha_\tau,\rho_\tau,\ell_\tau)$ \src{T}; shipped configuration $\Theta$ \src{S}; optional labels \src{L}
\State \textbf{Dispatch.} Send the list-first request (record list first, then counts ``for the records you listed''; allowed class names; row-by-row scan; native coordinate frame; no overlays) $K$ times, with $K$ set by the loss in $\Theta$; keep every attempt and its cost \src{T, S}
\State \textbf{Decode.} For each response, $H\mapsto(Z^{\mathrm{all}},Z,d,\sigma)$: audit records, delivered records, stated count, status L1 to L3 with the four degeneracy flags \src{O}
\State \textbf{Recover, at most once per call.} Transport failure (L1): resend the same request. Flagged response (L2 with no recoverable record, or a degeneracy flag): one follow-up that attaches the previous answer; keep it if unflagged, else keep the first response and its flags \src{S, O}
\State \textbf{Views.} Clicks: two-stage zoom on native pixels. Sets and counts: the whole image, or the views of an external view planner if one is configured, one call per view, records mapped to image coordinates \src{S, O}
\State \textbf{Construct.} Merge the reports of all views; map the delivered records of all calls to the final set $S$ with the construction $\Theta$ assigns to the loss (Table~\ref{tab:defaults}); a view confirms or rejects only records it contains \src{S}
\State \textbf{Read.} $\hat y\gets$ list count of $S$; if the list behind $S$ is flagged and $d\neq\varnothing$, $\hat y\gets d$ with status \texttt{count\_from\_statement}; clicks: the final point \src{O}
\State \textbf{Optional labels.} $\ge3$ labelled images: switch to a menu configuration only if its mean paired advantage minus one standard error is positive; 5 to 10 images: may fit the record gate \src{L}
\State \Return $S$, $\hat y$, readout branch, status $\sigma$, alarm score (disagreement with a second report, from a second model if configured), total cost of all attempts
\end{algorithmic}
\end{algorithm}

\paragraph{Inputs \src{T, S}.} The task fixes the class vocabulary $\mathcal{C}_\tau$, the alias map $\alpha_\tau$ (for example \{diamond, rhombus, rotated square\} $\mapsto$ square), the matching rule $\rho_\tau$ of Table~\ref{tab:contract} and the loss $\ell_\tau$. The loss selects the construction in Step 5. The shipped configuration fixes everything else that the algorithm calls a value: the prompt, the reasoning setting per model, the four flag thresholds, the recovery request, the view settings, the construction per loss, the alarm partner and the alarm thresholds. A model known to write degenerate lists at its lowest setting (Gemini 3.8) is run at its default setting, which at a fixed 16k output cap lowers its count readout error from 52.8 to 24.5 (Table~\ref{tab:setting}).

\paragraph{Steps 1 and 2: dispatch and decode.} The request asks for one JSON object in which the list of records comes first and \texttt{counts\_by\_type} follows, declared ``for the shapes you listed'' (Appendix~\ref{app:protocol} gives the prompt). The allowed class names are listed in the format; the model scans row by row from top to bottom and uses its native coordinate frame (0 to 1000 for GPT and Gemini; pixels for Sonnet, with the image pre-resized so that the provider does not resize it again). No grid, ticks or markers are drawn. The decoder keeps every recoverable record in the audit collection $Z^{\mathrm{all}}$ and passes the valid ones, after the alias map, to the delivered collection $Z$ (Section~\ref{sec:setup}). It sets four degeneracy flags on the list: more than 10\% of records without a valid class; a list length outside $[0.5,1.5]$ times the stated total; more than 10\% repeated coordinates; and the finish reason ``length''.

\paragraph{Step 3: bounded recovery.} The two kinds of failure get different recoveries. A transport failure, in which the call did not return, is a property of the connection and is resent unchanged. A flagged response is a property of how the model wrote this report, and errors of that kind persist (Section~\ref{sec:theory:behaviour}): in our detection experiments, resending a request whose flag had already repeated cleared the flag in 14.7\% of cases, while changing the request cleared it in 58.8\%. The change was a follow-up that attached the previous answer and asked for the complete answer under the same contract, or, for reports organised by image region, a new request for the flagged regions only. The pipeline sends the first kind of follow-up, once. If the follow-up still carries a flag, the first response is kept with its flags, and Step 6 decides how to read it. Every attempt enters the cost. The replay at the end of this section reports how often recovery was triggered and what the stored follow-ups changed.

\paragraph{Step 4: views.} For clicks, the first call gives a point on the whole screenshot. A crop one third of the screenshot's width and height, centred on that point and shifted to stay inside the image, is sent at native pixels, and the second call gives the point in the crop. If the second call gives no point, the first point is kept; if the first call gives no point, there is nothing to zoom on and the answer is no point, which counts as a miss. Using agreement to decide when to zoom costs more and is not more accurate (Section~\ref{sec:res:view}). For sets and counts, the pipeline does not plan views itself: it works on whatever reports it is given. By default it sends the whole image. When a \emph{view planner} is configured, for example a tiling scheme or the companion paper's safe decomposition, which places every target inside some view with neighbouring views overlapping by one object and cannot lower expected recall under that paper's monotonicity assumptions \citep{shi2026zoomin}, each view is one call, its records are mapped to image coordinates, and Step 5 merges them. Leaving the planner and its trigger to the configuration is a measured choice. We computed the apparent size of every annotated object in the whole-image calls on SCP-dense, DocLayNet, DOTA and SKU-110K, using the input geometry measured in the companion paper and its released calibration data (32-pixel tokens for GPT-6.1, 28-pixel tokens for Sonnet 5.5, a fixed grid of about 1,090 tokens for Gemini 3.8). The median object spans 0.62 to 1.43 tokens across its shorter side (the companion paper measures size as the square root of the area, which is never smaller). Below that paper's design value of $S^\star=1.5$ fall 55\% to 79\% of objects on the three detection sources and every shape on SCP-dense; yet GPT-6.1 and Sonnet 5.5 write nearly exact lists on SCP-dense. The companion paper likewise finds that these model families reach half recall at well under one token per object side. A fixed threshold would decompose images whose whole-image report is already complete, so when to call a planner is a property of the model and the task that the configuration supplies. These sizes come from the annotations and inform only this design choice; the pipeline reads no annotation at run time. Section~\ref{sec:res:view} reports how the pipeline handles reports from four crops, and how our own tiling arm, which did not meet the safe condition, fared on large objects.

\paragraph{Step 5: construction.} The construction is chosen per loss (Table~\ref{tab:defaults}). Records of different calls are associated without labels (Table~\ref{tab:contract}): boxes of the same class with IoU $\ge0.5$, screen elements at IoU $\ge0.5$ without class, and points of the same class within the task's tolerance. On over-reporting task families and set error, three calls are made and a record is kept only if all three report it, with its coordinates averaged over the three. Everywhere else a single call is delivered without deletion. Over- or under-reporting is a property of the task family, shipped with the configuration from our evaluation; the user does not supply it. Coordinate averaging is on by default because its contribution is positive in 37 of 54 base/partner pairs and negative in 13 (Table~\ref{tab:intersect}); the deletion-only variant is in the menu. Reports of several views are first merged into one report: the union of their records, where a record is dropped if it is associated with a record already kept from another view (a duplicate in an overlap). When reports from different views confirm one another, a view can confirm or reject only records that lie wholly inside it; a record that no partner view contains is kept, because that view carries no evidence about it (Section~\ref{sec:theory:behaviour}). A call that still has no readable answer after recovery counts as an empty report, so three-call unanimity keeps nothing on that image; this is the construction we evaluated, and dropping such a call from the support count is in the menu.

\paragraph{Step 6: readout.} The answer is read from the final set. For counts it is the list count of $S$, the number of records of each class. When the list behind $S$ carries a degeneracy flag and the response stated counts, the answer falls back to the stated count $d$, and the status says so (\texttt{count\_from\_statement}); a flagged list without stated counts keeps the list count and its flag. With several views, each response states counts for its own crop, and overlapping views would count shared objects twice; stated counts are therefore never combined across views, and a flagged merged list keeps the list count, with the status saying that no stated count was used. The fallback changes only the count: $S$ itself is not repaired, so the count and the set each carry their own status. Proposition~\ref{prop:readout} explains why the rule is a fallback and not a selector: a large gap between list count and stated count shows that the two readouts of one response are inconsistent, but by itself it does not say which one is closer to the truth. The flags are the evidence that the list is broken.

\paragraph{A second model \src{S}, optional.} When a second model is configured, its default role is the alarm of Step 8: its answer is compared with the user's, and items where they disagree by more than a threshold are flagged. The partner is fixed by a rule (GPT-6.1 and Sonnet 5.5: Gemini 3.8; Gemini 3.8: Sonnet 5.5), which picks the cheapest other model per click call (Appendix~\ref{app:protocol}), and the threshold $\delta$ is a point the user picks on the risk-coverage curve (Figure~\ref{fig:alarm}). Using the second model to confirm records is a menu option. The cross-model construction transferred from the other sources improves set error in 12 of 18 transfer cells and F1 in 10 of 18, and is worse in 2 and 3 cells; all of the worse cells are cells in which the user's own model is the strongest single model for that source and loss (Table~\ref{tab:transfer}). Because the user may not know whether that is the case, cross-model confirmation is chosen with labels or a shipped family-level ranking, not as a zero-label default.

\paragraph{Step 7: optional labels \src{L}.} Labels are never required. With fewer than three labelled images the pipeline keeps the shipped default and reports the labelled error. With three or more, it switches to another configuration from the menu only if that configuration's mean advantage over the labelled images, paired by image, minus one standard error is positive. For the decision to delete unconfirmed records, this rule predicts the better decision on the other images in 86\% to 88\% of draws with 3 to 10 labelled images, against 85\% for the family default alone (Section~\ref{sec:res:set}). With 5 to 10 labelled images it may also fit the record gate, a logistic selector on output features (Section~\ref{sec:res:select}). Certifying the accuracy of a pipeline on a population is a separate service: separating two pipelines that differ by 7 errors per image takes about 160 to 400 labelled images.

\paragraph{Step 8: delivery.} The pipeline returns the final set $S$, the answer $\hat y$, the readout branch, the status $\sigma$ (L1 to L3, flags, recovery used, views used), the alarm score when a second report exists, and the cost of every attempt.

\paragraph{One entry point, replayed on stored calls.} The repository implements Steps 1 to 6 and 8 of Algorithm~\ref{alg:pipeline}, including merging views and cross-view confirmation, as a single entry point (\texttt{fsr\_pipeline/}) whose branches read only the task specification, the shipped configuration and the responses a client returns; the label rule of Step 7 is a function in the same module, and the record gate is fitted by the analysis code of Section~\ref{sec:res:select}. A replay client serves the stored responses of this paper instead of calling a model. A request for which nothing was stored, such as a follow-up that was never sent, returns ``unavailable'', and the pipeline continues on its documented branch. Run on raw responses, the entry point reproduces the component analyses: per-type count error of 1.60 for GPT-6.1, 0.42 for Sonnet 5.5 and 24.52 for Gemini 3.8 at its default setting (52.80 at its lowest; Table~\ref{tab:setting}); click hit rates of 90.0\%, 87.0\% and 87.5\% after two-stage zoom on the 200 ScreenSpot-Pro items; and, with recovery switched off, the set error of the shipped construction in all 18 transfer cells to within 0.07 per image, a difference that comes from the 0.1-pixel coordinate rounding of the component analysis. Follow-ups were stored only for a sample of flagged detection calls. In the 18 set cells, 171 image runs had at least one flagged call; a stored follow-up cleared the flag in 24 of them, and replaying these changes set error by at most 0.55 per image in any cell. No follow-ups were stored for the count experiments, where 51 runs were flagged, so their results are those of the first call. Synthetic boundary cases go through the same code, and each produces an answer, a readout branch and a status: an empty or unreadable response, truncated JSON, a list without stated counts, a degenerate list with and without stated counts, two transport failures in a row, one unreadable call among three, and a click with no first point or no point in the crop. The replay output is released with the analysis outputs (\texttt{pipeline\_replay.json}).

\subsection{Revising the model from failed predictions}\label{sec:method:revise}

The theory was built by iteration, and the iteration is part of the method. A model is stated, a consequence is derived and tested, and when a prediction fails we record three things: which assumption failed and how we know; how the revised assumption was checked directly; and what new consequence the revision predicts, and whether it holds. Table~\ref{tab:revisions} lists the five revisions that shaped the final theory. Each row names the kind of evidence: an exact identity, a controlled comparison of interventions on the same images, or an association observed across cells or records.
