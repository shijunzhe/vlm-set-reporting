\section{Method: A Default Pipeline with Stated Inputs}\label{sec:method}

The default pipeline of FSR turns an image, a task specification and a budget into a final set, a task answer, a status and an alarm score; it needs no labels from the target task. A summary table in Section~\ref{sec:discussion} gives when each component helps, its measured effect and its cost. Every input it uses comes from one of three named sources, or is computed from the current responses: \src{task} the task specification and budget given by the user (classes, alias map, matching rule, loss); \src{config} the shipped configuration, a fixed file released with the code (\texttt{config/default\_pipeline.json}) whose values were chosen on our evaluation data and are carried unchanged to new images; and \src{labels} optional labelled images. No step requires the user to know $p_1$, a partner's quality or the current F1. Algorithm~\ref{alg:pipeline} gives the procedure; its comments name the steps described below. Steps 1 to 6 repair the report, the optional label rule of Step 7 judges between configurations, and the alarm of Step 8 detects errors. Section~\ref{sec:method:clicks} adds the GUI-grounding tier, a second tier for clicks that combines several models, and Section~\ref{sec:method:revise} describes how the model behind these steps was revised.

\begin{algorithm*}[t]
\caption{FSR default reporting pipeline. Tags give the source of each input: \src{task} the user's task specification and budget, \src{config} the shipped configuration file, \src{labels} optional labelled images; everything else is computed from the current responses. All calls append their response status and incurred cost to a shared execution trace; every return includes the accumulated trace and its cost $c$. A missing click is represented by an empty set and an explicit no-point status. Comments name the step paragraphs of Section~\ref{sec:method}.}\label{alg:pipeline}
\small
\begin{algorithmic}[1]
\Require image $x$; task $\tau=(\mathcal{C}_\tau,\alpha_\tau,\rho_\tau,\Omega_\tau,\ell_\tau)$ and budget $B$ per item \src{task}; configuration $\Theta$ \src{config}; optional labelled images $\mathcal{D}_L$ \src{labels}
\Ensure final set $S$, answer $\hat y$, status $\sigma$ (readout branch, flags, recovery, views), alarm score $a$ (\emph{not computed} without a partner), cost $c$ of every attempt
\If{$|\mathcal{D}_L|\ge3$} \Comment{Step 7, before inference; never required}
  \State replace $\Theta$ by a menu configuration only if its mean paired advantage over $\Theta$ on $\mathcal{D}_L$ minus one standard error is positive
\EndIf
\State select the interface $\eta$ (model, setting, prompt, schema), the number of calls $K$ and the views $\mathcal{V}$ from $(\tau,B,\Theta)$ \Comment{Step 1}
\If{$\tau$ asks for one click}
  \If{$B$ covers the planned worst case of Algorithm~\ref{alg:clicks}}
    \State $(\hat p,\sigma,\mathit{alarm})\gets$ Algorithm~\ref{alg:clicks}$(x,\tau,B,\Theta)$;\ \ $\hat y\gets\hat p$;\ \ $a\gets\mathit{alarm}$ (1 or 0)
    \State $S\gets\{\hat p\}$, or $\varnothing$ if there is no point;\ \ \Return $S,\hat y,\sigma,a,c$
  \EndIf
  \State $\hat p\gets\textsc{Zoom}(x,\eta)$;\ \ $\hat y\gets\hat p$;\ \ $S\gets\{\hat p\}$, or $\varnothing$ with status no point \Comment{Step 4; no point is a miss}
\Else
  \For{$k=1,\dots,K$ and each view $v\in\mathcal{V}$} \Comment{$\mathcal{V}=\{x\}$ unless a view planner is configured}
    \State $R_{k,v}=(Z^{\mathrm{all}}_{k,v},Z_{k,v},d_{k,v},\sigma_{k,v})\gets\textsc{Report}(v,\eta)$, records mapped to image coordinates \Comment{Steps 2 and 3}
  \EndFor
  \State $R_k\gets$ merge of $R_{k,v}$ over $v$, dropping a record associated with one already kept from another view
  \State $S\gets C(R_1,\dots,R_K)$ with the construction $\Theta$ assigns to $\ell_\tau$; a view confirms only records inside it \Comment{Step 5}
  \State $\hat y\gets r_\tau(S)$, for counts the list count of $S$ \Comment{Step 6}
  \If{$\tau$ is a count task, $|\mathcal{V}|=1$, $\sigma_{1,x}$ flags the list of $R_1$ and its stated counts $d_{1,x}\neq\varnothing$}
    \State $\hat y\gets d_{1,x}$;\ \ readout branch $\gets$ \texttt{count\_from\_statement}
  \EndIf
  \State $\sigma\gets$ the readout branch, the call statuses $\sigma_{k,v}$ (flags, recovery used) and the views used
\EndIf
\If{a partner model is configured} \Comment{Step 8, alarm}
  \State $\hat y'\gets$ the same steps run by the partner with one call per view;\ \ $a\gets\mathrm{dis}_\tau(\hat y,\hat y')$
\Else
  \State $a\gets$ \emph{not computed}
\EndIf
\State \Return $S,\hat y,\sigma,a,c$
\Statex
\Function{Report}{$v,\eta$} \Comment{one call with bounded recovery}
  \State $H\gets$ call $\eta$ on $v$; on a transport failure (L1) resend once; if it fails again, \Return an empty report with status L1
  \State $(Z^{\mathrm{all}},Z,d,\sigma)\gets D_{\eta,\tau}(H)$ \Comment{$d$: stated counts; $\sigma$: this call's status, with the four degeneracy flags}
  \If{$\sigma$ is flagged or the response has no readable answer}
    \State $H'\gets$ one follow-up that attaches $H$; \textbf{if} $D_{\eta,\tau}(H')$ is readable and unflagged \textbf{then} \Return $D_{\eta,\tau}(H')$
  \EndIf
  \State \Return $(Z^{\mathrm{all}},Z,d,\sigma)$
\EndFunction
\Statex
\Function{Zoom}{$x,\eta$} \Comment{two-stage zoom in the style of ReGround}
  \State $q_1\gets$ point from one call on $x$ (resend once on L1); if there is none, \Return no point
  \State $w\gets$ crop of one third of the width and height of $x$, centred on $q_1$, shifted inside $x$, at native pixels
  \State $q_2\gets$ point from one call on $w$ (resend once on L1), mapped to $x$;\ \ \Return $q_2$ if it exists, else $q_1$
\EndFunction
\end{algorithmic}
\end{algorithm*}

\paragraph{Inputs \src{task, config}.} The task fixes the class vocabulary $\mathcal{C}_\tau$, the alias map $\alpha_\tau$ (for example \{diamond, rhombus, rotated square\} $\mapsto$ square), the matching rule $\rho_\tau$ of Table~\ref{tab:contract}, the ignore region $\Omega_\tau$ and the loss $\ell_\tau$. The loss selects the construction in Step 5. The user also gives a budget per item. The shipped configuration fixes everything else that the algorithm calls a value: the prompt, the reporting interface and reasoning setting per model and loss (Table~\ref{tab:defaults}), the four flag thresholds, the recovery request, the view settings, the construction per loss, the alarm partner, the default alarm threshold, and the models, settings, distance, scorer and number of compared clusters of Algorithm~\ref{alg:clicks}. For counts, a model known to write degenerate lists at its lowest setting (Gemini 3.8) is run at its default setting (Section~\ref{sec:res:degen}).

\paragraph{Steps 1 and 2: dispatch and decode.} Step 1 is a dispatcher, not one fixed request: what is shared across tasks is the chain of records, losses and readouts, not one output format. For set tasks scored by F1 the shipped configuration may select the regions interface, in which the model returns one row per region of a fixed coordinate registry (Appendix~\ref{app:protocol}). The count request asks for one JSON object in which the list of records comes first and \texttt{counts\_by\_type} follows, declared ``for the shapes you listed'' (Appendix~\ref{app:protocol} gives the prompt). The allowed class names are listed in the format; the model scans row by row from top to bottom and uses its native coordinate frame (0 to 1000 for GPT and Gemini; pixels for Sonnet, with the image pre-resized so that the provider does not resize it again). No grid, ticks or markers are drawn. The decoder keeps every recoverable record in the audit collection $Z^{\mathrm{all}}$ and passes the valid ones, after the alias map, to the delivered collection $Z$ (Section~\ref{sec:setup}). It sets four degeneracy flags on the list: more than 10\% of records without a valid class; a list length outside $[0.5,1.5]$ times the stated total; more than 10\% repeated coordinates; and the finish reason ``length''.

\paragraph{Step 3: bounded recovery.} The two kinds of failure get different recoveries. A transport failure, in which the call did not return, is a property of the connection and is resent unchanged. A flagged response is a property of how the model wrote this report, and such errors tend to recur, consistent with Section~\ref{sec:theory:behaviour}: in our detection experiments, resending a request whose flag had already repeated cleared the flag in 14.7\% of cases, while changing the request cleared it in 58.8\%. The change was a follow-up that attached the previous answer and asked for the complete answer under the same contract, or, for reports organised by image region, a new request for the flagged regions only. The pipeline sends the first kind of follow-up, once. If the follow-up still carries a flag, the first response is kept with its flags, and Step 6 decides how to read it. Every attempt enters the cost. The replay at the end of this section reports how often recovery was triggered and what the stored follow-ups changed.

\paragraph{Step 4: views.} For clicks we use a re-grounding strategy in the style of the ReGround method that \citet{li2025screenspotpro} evaluate. The first call gives a point on the whole screenshot. A crop one third of the screenshot's width and height, centred on that point and shifted to stay inside the image, is sent at native pixels, and the second call gives the point in the crop. If the second call gives no point, the first point is kept; if the first call gives no point, there is nothing to zoom on and the answer is no point, which counts as a miss. Using agreement to decide when to zoom costs more and is not more accurate (Section~\ref{sec:res:view}). For sets and counts, the pipeline does not plan views itself: it works on whatever reports it is given. By default it sends the whole image. When a \emph{view planner} is configured, for example a tiling scheme or the companion paper's safe decomposition, which places every target wholly inside some view, with neighbouring views overlapping by one object and no view having fewer tokens per object than the whole image, and cannot lower expected recall under that paper's monotonicity assumptions \citep{shi2026zoomin}, each view is one call, its records are mapped to image coordinates, and Step 5 merges them. We computed the apparent size of every annotated object in the whole-image calls on SCP-dense, DocLayNet, DOTA and SKU-110K, using the input geometry measured in the companion paper and its released calibration data (32-pixel tokens for GPT-6.1, 28-pixel tokens for Sonnet 5.5, a fixed grid of about 1,090 tokens for Gemini 3.8). The median object spans 0.62 to 1.43 tokens across its shorter side (the companion paper measures size as the square root of the area, which is never smaller). Below that paper's design value of $S^\star=1.5$ fall 55\% to 79\% of objects on the three detection sources and every shape on SCP-dense; yet GPT-6.1 and Sonnet 5.5 write nearly exact lists on SCP-dense. The companion paper likewise finds that these model families reach half recall at well under one token per object side. A fixed threshold would decompose images whose whole-image report is already complete, so when to call a planner is a property of the model and the task that the configuration supplies. These sizes come from the annotations and inform only this design choice; the pipeline reads no annotation at run time. Section~\ref{sec:res:view} reports how the pipeline handles reports from four crops, and how our own tiling arm, which did not meet the safe condition, fared on large objects.

\paragraph{Step 5: construction.} The construction is chosen per loss (Table~\ref{tab:defaults}). Records of different calls are associated without labels (Table~\ref{tab:contract}): boxes of the same class with IoU $\ge0.5$, screen elements at IoU $\ge0.5$ without class, and points of the same class within the task's tolerance. On over-reporting task families and set error, three calls are made and a record is kept only if all three report it, with its coordinates averaged over the three. Everywhere else a single call is delivered without deletion. Over- or under-reporting is a property of the task family, shipped with the configuration from our evaluation; the user does not supply it. Coordinate averaging is on by default because its contribution is positive in 37 of 54 base/partner pairs and negative in 13 (Section~\ref{sec:res:set}); the deletion-only variant is in the menu. Reports of several views are first merged into one report: the union of their records, where a record is dropped if it is associated with a record already kept from another view (a duplicate in an overlap). When reports from different views confirm one another, a view can confirm or reject only records that lie wholly inside it; a record that no partner view contains is kept (Section~\ref{sec:theory:behaviour}). A call that still has no readable answer after recovery counts as an empty report, so three-call unanimity keeps nothing on that image; this is the construction we evaluated, and dropping such a call from the support count is in the menu.


\begin{algorithm*}[t]
\caption{GUI-grounding tier of FSR: clicks from several models. Called by Algorithm~\ref{alg:pipeline} only when the budget covers its planned worst case. Comments give the term of Proposition~\ref{prop:three} that each step acts on and the number of calls.}\label{alg:clicks}
\small
\begin{algorithmic}[1]
\Require screenshot $x$, instruction, budget $B$ \src{task}; models $M_1,\dots,M_J$ with their settings, scorer $M_s$, distance $\delta$, number of compared clusters $m_{\max}$, model order \src{config}
\Ensure point $\hat p$ or no point (a miss); status $\sigma$ (no candidate, one cluster, or the comparison outcome); alarm flag (1 if the candidates form two or more clusters, else 0); cost $c$ of every attempt
\Statex \emph{Shipped instance:} $J=3$ (GPT-6.1 and Sonnet 5.5 at the default setting, Gemini 3.8 at the lowest), $M_s$ = Gemini 3.8 at the lowest setting, $\delta=1.5\%$ of the longer side, $m_{\max}=3$; planned worst case $3J+2\binom{m_{\max}}{2}=15$ calls, technical retries excluded.
\For{$j=1,\dots,J$} \Comment{generate, acts on $F$; $2J$ calls}
  \State $p_j\gets\textsc{Zoom}(x,M_j)$ (Algorithm~\ref{alg:pipeline}); if $p_j$ exists, register it as a candidate whose identifier is bound to its coordinates on $x$, its model, setting and call
\EndFor
\If{there is no candidate} \Return no point \EndIf
\State $Q_1,\dots,Q_n\gets$ connected components of the graph that joins candidates within $\delta$;\ \ alarm $\gets(n\ge2)$ \Comment{detect}
\For{each candidate $j$} \Comment{represent, acts on $L$; $J$ calls}
  \State $s_j\gets$ hit score in $[0,1]$ from $M_s$ on a native crop with candidate $j$ marked; a missing or unreadable score counts as $-1$
\EndFor
\State representative of each $Q_i\gets$ its member with the highest $s_j$, ties broken by the model order
\If{$n=1$} \Return the representative of $Q_1$ \Comment{no alarm, no comparison}
\EndIf
\State rank the clusters by (representative's $s_j$, cluster size, earliest model in the cluster)
\For{each pair of the first $m_{\max}$ clusters, in both orders} \Comment{compare, acts on $W$; at most $2\binom{m_{\max}}{2}$ calls}
  \State $M_s$ sees both representatives marked by identifier, on the downscaled screenshot and on a native crop around each, and names the one that hits the target
\EndFor
\State a representative wins a pair only if both orders name it; a failed, undecided or split pair gives no win
\State \Return the representative of the cluster with the most wins, ties broken by the ranking; if no cluster has a win, the first cluster of the ranking
\end{algorithmic}
\end{algorithm*}

\paragraph{Step 6: readout.} The answer is read from the final set. For counts it is the list count of $S$, the number of records of each class. When the list behind $S$ carries a degeneracy flag and the response stated counts, the answer falls back to the stated count $d$, and the status says so (\texttt{count\_from\_statement}); a flagged list without stated counts keeps the list count and its flag. With several views, each response states counts for its own crop, and overlapping views would count shared objects twice; stated counts are therefore never combined across views, and a flagged merged list keeps the list count, with the status saying that no stated count was used. The fallback changes only the count: $S$ itself is not repaired, so the count and the set each carry their own status. The flags, not the readout gap, trigger the fallback, because a gap shows that the two readouts disagree without saying which is right (Proposition~\ref{prop:readout}).

\paragraph{A second model \src{config}, optional.} When a second model is configured, its default role is the alarm of Step 8: its answer is compared with the user's, and items where they disagree by more than a threshold are flagged. The disagreement $\mathrm{dis}_\tau$ is the summed per-class difference of the two answers for counts, the number of records not associated across the two answers for sets (Table~\ref{tab:contract}), and the distance between the two points as a share of the longer image side for clicks, where a missing point always raises the alarm. The partner is fixed by a rule (GPT-6.1 and Sonnet 5.5: Gemini 3.8; Gemini 3.8: Sonnet 5.5), which picks the cheapest other model per click call (Appendix~\ref{app:protocol}), and the threshold $\delta$ is a point the user picks on the risk-coverage curve (Section~\ref{sec:res:persist}; shipped default 1.5\%). Using the second model to confirm records is a menu option, chosen with labels or a shipped family-level ranking rather than as a zero-label default, because it is worse only in cells where the user's own model is the strongest (Section~\ref{sec:res:transfer}).

\paragraph{Step 7: optional labels \src{labels}.} Labels are never required. With fewer than three labelled images the pipeline keeps the shipped default and reports the labelled error. With three or more, it switches to another configuration from the menu only if that configuration's mean advantage over the labelled images, paired by image, minus one standard error is positive. Section~\ref{sec:res:set} evaluates this rule for the decision to delete unconfirmed records. With 5 to 10 labelled images it may also fit the record gate, a logistic selector on output features (Section~\ref{sec:res:select}). Certifying the accuracy of a pipeline on a population is a separate service that needs its own labelled sample.

\paragraph{Step 8: delivery.} The pipeline returns the final set $S$, the answer $\hat y$, the readout branch, the status $\sigma$ (L1 to L3, flags, recovery used, views used), the alarm score when a second report exists, and the cost of every attempt.

\paragraph{One entry point, replayed on stored calls.} The repository implements Steps 1 to 6 and 8 of Algorithm~\ref{alg:pipeline} for counts, sets and single-model clicks, including merging views and cross-view confirmation, as a single entry point (\texttt{fsr\_pipeline/}) whose branches read only the task specification, the shipped configuration and the responses a client returns; the label rule of Step 7 is a function in the same module, and the record gate is fitted by the analysis code of Section~\ref{sec:res:select}. Algorithm~\ref{alg:clicks} runs as a separate function (\texttt{gui/code/decision.py}), and the per-model F1 configuration is a key of the shipped configuration file evaluated by the analysis of Section~\ref{sec:res:transfer}; neither is a branch of this entry point. A replay client serves the stored responses of this paper instead of calling a model. A request for which nothing was stored, such as a follow-up that was never sent, returns ``unavailable'', and the pipeline continues on its documented branch. Run on raw responses, the entry point reproduces the component analyses: the count errors of Sections~\ref{sec:res:readout} and \ref{sec:res:degen}, the click hit rates after two-stage zoom of Section~\ref{sec:res:view}, and, with recovery switched off, the set error of the shipped construction in all 18 transfer cells to within 0.07 per image, a difference that comes from the 0.1-pixel coordinate rounding of the component analysis. Follow-ups were stored for a sample of flagged detection calls. In the 18 set cells, 171 image runs had at least one flagged call; a stored follow-up cleared the flag in 24 of them, and replaying these changes set error by at most 0.55 per image in any cell. No follow-ups were stored for the count experiments, where 51 runs were flagged, so their results are those of the first call. Synthetic boundary cases go through the same code, and each produces an answer, a readout branch and a status: an empty or unreadable response, truncated JSON, a list without stated counts, a degenerate list with and without stated counts, two transport failures in a row, one unreadable call among three, and a click with no first point or no point in the crop. The replay output is released with the analysis outputs (\texttt{pipeline\_replay.json}).

\subsection{GUI grounding: clicks from several models}\label{sec:method:clicks}

Algorithm~\ref{alg:pipeline} delivers one model's two-stage zoom point. When the per-item budget covers the planned worst case of a second tier, the pipeline offers one built on the three sources of a miss (Proposition~\ref{prop:three}); its mean cost is about 3.2 times that of one zoom. Its run-time inputs are the image, the instruction and the budget; it reads no target label and does not abstain. The models, their settings, the distance $\delta$, the scorer and the number of compared clusters come from the shipped configuration \src{config}.



Algorithm~\ref{alg:clicks} gives the steps, organised by Proposition~\ref{prop:three}. Generation enlarges the candidate menu, which is the only way to lower $F$; Section~\ref{sec:res:choose} measures the rescue rate of each source on the others' misses (Proposition~\ref{prop:coverage}). The representative step fixes which member of each cluster can be output, and the comparison chooses among representatives, so these two steps divide the remaining misses between $L$ and $W$. The comparison runs only on items with an alarm, where the measured miss rate of the scorer's choice is highest (Sections~\ref{sec:theory:points} and \ref{sec:res:choose}); items whose candidates form one cluster keep that cluster's representative. The scorer's hit score is used only to rank. The registry makes the point that is scored, drawn, compared and returned the same point: every step refers to a candidate by its identifier, and the code asserts that the coordinates drawn for the scorer equal those returned. If a call fails, the procedure continues with the remaining candidates. It returns no point only when no candidate is available; a missing point counts as a miss, and every returned point is scored by the hit-in-target rule. The budget selects among planned call schedules before inference: the tier runs only if the budget covers its planned worst case of 15 calls at per-call output caps of 16,384 tokens at the lowest setting and 32,768 at the default. Technical retries are outside this bound, and the per-item costs we report are realized averages over all attempts, retries included. The rules are implemented as one deterministic function over stored or live responses (\texttt{gui/code/decision.py} in the release), with request builders for each step; with the evaluation script, run on the stored responses, it regenerates the results of Section~\ref{sec:res:choose}.

\subsection{Revising the model from failed predictions}\label{sec:method:revise}

The theory was built by iteration, and the iteration is part of the method. A model is stated, a consequence is derived and tested, and when a prediction fails we record three things: which assumption failed and how we know; how the revised assumption was checked directly; and what new consequence the revision predicts, and whether it holds. Table~\ref{tab:revisions} lists the five revisions that shaped the final theory. Each row names the kind of evidence: an exact identity, a controlled comparison of interventions on the same images, or an association observed across cells or records.
